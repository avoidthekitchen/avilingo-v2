## Addendum: shipping build's algorithm question

Follow-up evidence for archive **2.0.0 (1)**: `iosIsEncryption=false`; databases open unencrypted without a key. The embedded SQLCipher framework dynamically links libSystem, CoreFoundation, and Security. Its imported cryptographic symbols are Apple's CCCryptor, CCHmac, CCKeyDerivationPBKDF, and SecRandomCopyBytes APIs. No additional dynamic crypto library was found. The resolved SQLCipher package is 4.19.0.

**What this establishes:** CommonCrypto is an Apple OS cryptographic interface. SQLCipher 4.19.0's CommonCrypto provider delegates AES-256-CBC, HMAC, PBKDF2, and randomness to those Apple APIs, matching the archive imports. It does not implement those primitives itself in that provider. This supports an **OS-provided algorithms** interpretation, rather than assuming that every SQLCipher build necessarily ships an independent AES implementation. Imports alone cannot rule out every statically embedded implementation elsewhere in the app. [Apple cryptographic interfaces](https://developer.apple.com/security/), [SQLCipher 4.19.0 provider source](https://github.com/sqlcipher/sqlcipher/blob/v4.19.0/src/crypto_cc.c)

Apple's reference says OS-only encryption requires no App Store Connect documentation; it distinguishes industry-standard algorithms **not provided within Apple's OS**. Therefore **“None of the algorithms mentioned above” is the better-supported technical answer to this particular radio question if the archive audit confirms OS-only cryptographic implementations throughout**. Here “None” means neither proprietary/nonstandard algorithms nor standard algorithms implemented outside Apple's OS; it does not declare that the app contains no encryption-related code. Choosing “Standard” merely because SQLCipher has AES capability would ignore the question's OS distinction. This is an inference from Apple's categories and the implementation evidence, not an Apple ruling on this binary. [Apple documentation categories](https://developer.apple.com/help/app-store-connect/reference/app-information/export-compliance-documentation-for-encryption/)

**What remains separate:** this radio answer concerns Apple's documentation workflow, not the app's full export classification. Disabled database encryption does not automatically remove a linked library from consideration. BIS defines dormant cryptography/activation more specifically than a runtime configuration flag and states that incorporated libraries do not transfer their classifications to a new product. Zetetic's general export guidance similarly leaves responsibility with the app developer. These sources do not conclusively classify this app with its encryption mode disabled. [BIS encryption FAQ, Q4/Q14](https://media.bis.gov/media/documents/encryption-faqs.pdf), [SQLCipher export guidance](https://www.zetetic.net/sqlcipher/export-compliance/)

Owner checklist before saving the answer:

1. Confirm the declaration applies to the audited **2.0.0 (1)** archive, not a different upload.
2. Confirm the whole-app audit finds no proprietary crypto or additional non-OS algorithm implementation, including static dependencies and JavaScript.
3. Review the OS-only inference above and distinguish it from claiming “no cryptography”; save **None** only if that accurately describes the app.
4. Record the selected answer and Apple's resulting documentation requirement. If the owner needs an authoritative determination about the bundled, inactive SQLCipher capability or remaining export obligations, provide these exact facts to Apple's export process/BIS; do not substitute a blanket exemption claim. No inquiry or declaration was submitted during research. [Apple's determination/contact workflow](https://developer.apple.com/help/app-store-connect/manage-app-information/determine-and-upload-app-encryption-documentation/)
